# Coding Conventions

**Analysis Date:** 2026-06-09

## Repo Type

This is a **content-only Cinatra agent extension** repo. There are no `src/` TypeScript sources — the agent logic lives entirely in the LLM system prompt at `skills/contact-discovery-agent/SKILL.md` and the machine-readable OAS at `cinatra/oas.json`. The only runtime code file is `extension-kind-gate.mjs`, a zero-dependency CI gate utility shipped by the extraction script.

## Naming Patterns

**Files:**
- Extension artifacts use lowercase-hyphenated names: `extension-kind-gate.mjs`, `oas.json`, `workflow.bpmn`
- Skills directory mirrors the package slug: `skills/contact-discovery-agent/SKILL.md`
- All artifacts under `cinatra/` use lowercase

**Functions (in `extension-kind-gate.mjs`):**
- Exported pure functions: `camelCase` with descriptive verb prefix — `validateAgent`, `validateWorkflow`, `validateWorkflowPackageShape`, `validateBpmnSanity`, `findWorkflowSidecars`, `runGate`, `parseArgs`
- Internal helpers: `camelCase` — `walkLlmStrings`, `scanOasString`, `wordBoundary`
- Entry point: `main()`

**Variables:**
- `camelCase` throughout: `packageRoot`, `oasPath`, `bpmnPrefixes`, `rootName`, `rootAttrs`, `openTags`
- Constants: `SCREAMING_SNAKE_CASE` for module-level sets and arrays — `BANNED_PRIMITIVES`, `BANNED_TYPEHINTS`, `LLM_VISIBLE_FIELDS`, `PRIMITIVE_PATTERNS`, `OBJECTS_LIST_CRM_RE`, `BPMN_MODEL_NS`, `WORKFLOW_PACKAGE_NAME_RE`

**Types:**
- No TypeScript in this repo (content-only). `extension-kind-gate.mjs` is plain ESM JavaScript.

## Prompt / SKILL.md Conventions

**LLM prompt style (`skills/contact-discovery-agent/SKILL.md`):**
- Structured as numbered Steps (Step 1–5) with clear headers
- Input/output contracts defined in a YAML front matter block (`name`, `description`)
- JSON return shape documented with inline code fences
- All error paths explicitly enumerated inline; no ambiguity about what to return on failure
- Defensive caps documented with explicit formulas (`Math.min(maxContacts, 5)`)
- Tool discipline section lists EXACTLY which MCP primitives are allowed — forbidden calls named explicitly

**OAS (`cinatra/oas.json`):**
- LLM-visible fields: `system`, `user`, `description` — scanned by the CI gate for banned primitives
- Inputs/outputs typed as JSON Schema fragments with explicit defaults

## Code Style (`extension-kind-gate.mjs`)

**Formatting:**
- No formatter config detected (no `.prettierrc`, no `biome.json`, no `.eslintrc`)
- Style is consistent: 2-space indentation, double quotes for strings, trailing commas in arrays/objects
- Arrow functions preferred for callbacks and short lambdas
- Template literals used for error message interpolation

**Linting:**
- No ESLint/Biome config detected — this file is auto-generated by the extraction script and treated as a sealed artifact

**Module system:**
- ESM (`"type": "module"` in `package.json`)
- Only Node built-ins imported: `node:fs`, `node:path`
- No third-party dependencies — enforced by design (CI runs before any registry is reachable)

## Import Organization

**Order (in `extension-kind-gate.mjs`):**
1. Named imports from Node built-ins only — `import { readFileSync, existsSync, readdirSync } from "node:fs"` and `import { resolve, join, basename, dirname, relative } from "node:path"`
2. No external imports (zero-dependency constraint)

**Path Aliases:**
- None — single-file utility, no aliasing needed

## Error Handling

**Patterns:**
- Pure functions return `string[]` errors rather than throwing — callers accumulate and report
- `try/catch` wraps all I/O calls (`readFileSync`, `readdirSync`); errors are stringified via `err instanceof Error ? err.message : String(err)` and pushed to the errors array
- The gate's `main()` is the only throw boundary: wrapped in `try/catch` with `process.exit(1)` on unexpected errors
- In the LLM prompt: Step 1 (`account_not_found`) is the only abort path; Steps 2–4 accumulate failures into `failures[]` without aborting — consistent best-effort error capture

## Logging

**Framework:** `console` (no logging library)

**Patterns:**
- Success: `console.log(...)` with a `✓` prefix
- Violations: `console.error(...)` with a `✗` prefix and bullet points (`•`)
- In CI workflow: structured `echo` statements to `$GITHUB_ENV` for step-to-step variable passing

## Comments

**When to Comment:**
- Section dividers use `// ---...---` banners with a title and explanation
- Inline comments explain non-obvious constraints (e.g., why `pnpm dlx` is not used, why `apollo_administration_get` is preferred over `apollo_validate`)
- `"//":` JSON comments in `tsconfig.json` for human-readable explanation of design decisions

**JSDoc/TSDoc:**
- JSDoc-style block comments on exported functions explaining purpose, inputs, outputs, and key constraints — e.g., `/** Validate an agent extension at packageRoot. Pure: returns string[] errors. */`

## Function Design

**Size:** Functions are small and single-purpose; the largest (`validateBpmnSanity`) is ~80 lines, handling one well-scoped validation concern

**Parameters:** Simple scalar or single-object parameters; no complex parameter bags

**Return Values:** All validation functions return `string[]` (errors) consistently; `runGate` returns `{ kind, errors }`

## Module Design

**Exports:** Named exports only — `parseArgs`, `validateAgent`, `validateWorkflowPackageShape`, `validateBpmnSanity`, `findWorkflowSidecars`, `validateWorkflow`, `runGate` (from `extension-kind-gate.mjs`)

**Barrel Files:** Not applicable — single-file module

**Invocation Guard:** Uses `process.argv[1]` vs `import.meta.url` comparison to guard `main()` so the file is safely importable in tests without side effects
